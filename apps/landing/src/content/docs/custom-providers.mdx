# Custom Providers

Orchestra supports multiple AI providers through a unified interface. Each provider connects to a different AI backend, and Orchestra handles routing, fallback, encryption, and cost tracking across all of them.

## Supported Providers

| Provider | API Endpoint | Auth Method | Models | Status |
|---|---|---|---|---|
| `openai` | `api.openai.com/v1` | `Authorization: Bearer` | GPT-4o, GPT-4o-mini, GPT-4.1 | Available |
| `anthropic` | `api.anthropic.com/v1` | `x-api-key` header | Claude Sonnet 4, Claude 3.5 Haiku | Available |
| `openrouter` | `openrouter.ai/api/v1` | `Authorization: Bearer` | All models (100+) | Available |
| `opencode-go` | `opencode.ai/zen/go/v1` | `Authorization: Bearer` | 10 Go models (free tier) | Available |
| `google` |  -- |  -- |  -- | Not implemented |
| `aws_bedrock` |  -- |  -- |  -- | Not implemented |
| `azure_openai` |  -- |  -- |  -- | Not implemented |
| `custom` |  -- |  -- |  -- | Not implemented |
| `mock` | No network | None | `mock-blueprint-v1` | Available (testing) |

> [!NOTE]
> The `google`, `aws_bedrock`, `azure_openai`, and `custom` provider types are defined in the schema but not yet implemented. Attempting to use them will return a validation error.

### Mock Provider

A testing provider that requires no network access and returns a hardcoded blueprint.

```
Network:  None
Auth:     None (API key ignored)
Validate: Always returns valid
Model:    mock-blueprint-v1
```

The mock provider returns a complete blueprint with all 12 lifecycle phases, sample assumptions, constraints, risks, and a roadmap. It simulates a 50ms processing delay.

> [!WARNING]
> The mock provider is for development and testing only. It returns identical output regardless of interview answers. Do not use it for real project planning.

## Adding a Provider Credential

### Via the API

```bash
# Create a credential
curl -X POST http://localhost:3000/api/v1/provider-credentials \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "openai",
    "apiKey": "sk-...",
    "defaultModel": "gpt-4o-mini"
  }'

# Validate the credential
curl -X POST http://localhost:3000/api/v1/provider-credentials/<id>/validate
```

### Via the UI

1. Navigate to **Settings** in the Orchestra web interface
2. Select **Providers** from the sidebar
3. Click **Add Provider**
4. Choose a provider type from the dropdown
5. Enter your API key
6. Optionally set a default model
7. Click **Save** to store the credential
8. Click **Validate** to test the connection

> [!TIP]
> After adding a credential, always validate it. Validation confirms the API key works and discovers available models. An unvalidated credential has status `unverified` and may not be selected by the router.

### Credential Lifecycle

```
Created →unverified
         →    Validate →valid (success)
             →invalid (bad key)
             →failed (connection error)
         →    Update API key →unverified (re-validates)
```

| Status | Meaning |
|---|---|
| `unverified` | Credential created but not yet validated |
| `valid` | API key confirmed working |
| `invalid` | API key rejected by provider |
| `expired` | API key expired (provider-specific) |
| `rate_limited` | Too many validation attempts |
| `failed` | Connection or unknown error |

## Provider Validation

When you validate a credential, Orchestra makes a real API call to the provider to confirm the key works.

### How It Works

Each provider has a provider-specific validation strategy:

| Provider | Validation Method |
|---|---|
| `openai` | `GET /models`  -- lists available GPT models |
| `anthropic` | `GET /models`  -- lists available Claude models |
| `openrouter` | `GET /auth/key` + `GET /models`  -- checks key and lists models |
| `opencode-go` | `POST /chat/completions`  -- sends "Say OK" test message (30s timeout) |
| `mock` | Always returns `{ valid: true }` |

On success, the credential status is set to `valid` and available models are stored. On failure, the status is set to `invalid` and the error message is recorded.

### Rate Limiting

Provider validation is rate-limited to prevent abuse:

```
Max requests: 20 per 60 seconds (per credential)
```

> [!DANGER]
> Exceeding the validation rate limit returns a `429 Too Many Requests` error with a `Retry-After` header. Repeated violations may lock the credential.

## Encryption at Rest

API keys are encrypted before being stored in the database using AES-256-GCM.

### Configuration

```bash
# Generate a 32-byte encryption key
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# Set it as an environment variable
export ENCRYPTION_KEY="your-64-character-hex-key"
```

### Encryption Details

| Parameter | Value |
|---|---|
| Algorithm | AES-256-GCM |
| Key derivation | SHA-256 hash of `ENCRYPTION_KEY` env var |
| IV | Random 16 bytes per encryption |
| Auth tag | 16 bytes (GCM authentication) |
| Serialized format | `<iv>:<ciphertext>:<tag>` (hex-encoded, colon-separated) |

### Storage Format

Encrypted keys are stored as a single string in the format:

```
<16-byte-iv-hex>:<ciphertext-hex>:<16-byte-tag-hex>
```

The ciphertext may contain colons (since the ciphertext itself is hex-encoded and could produce colon characters), so parsing splits on the first and last colons only.

> [!WARNING]
> Without `ENCRYPTION_KEY` set, credentials are still stored but **not encrypted**. The API key is stored as-is. Always set `ENCRYPTION_KEY` in production environments.

> [!DANGER]
> If you change `ENCRYPTION_KEY` after storing credentials, all existing encrypted keys become undecryptable. Back up your encryption key securely.

## Model Routing and Fallback Chains

Orchestra uses a router to select the best provider and model for each task. The router considers:

- **Task type**: `blueprint`, `prompt_generation`, `architecture`, `roadmap`, `summary`, `clarification`
- **User preferences**: Preferred provider and model
- **Provider availability**: Only validated credentials are selected
- **Model tier**: `cheap`, `balanced`, or `strong`

### Fallback Chain

If the primary provider fails, the router automatically falls back through a chain:

```
Primary selection →Fallback 1 →Fallback 2 →...
```

Each fallback attempt:

1. Detects the failure (network error, rate limit, invalid response)
2. Selects the next model in the fallback chain
3. Retries the generation with the new provider
4. Continues until success or chain exhaustion

> [!TIP]
> Configure multiple provider credentials to maximize fallback options. If OpenAI is down, having Anthropic and OpenRouter credentials means the router can fall back automatically.

### Retry Behavior

Both risk resolution and blueprint refinement use retry loops:

| Operation | Max Attempts | Retry On |
|---|---|---|
| Risk resolution (prompt rewrite) | 2 | Provider error, short response, parse failure |
| Blueprint refinement | 3 | Provider error, parse failure, Zod validation failure |
| Provider validation | 1 | No retry (single attempt) |

## OpenCode Go Provider Details

The OpenCode Go provider (`opencode-go`) is Orchestra's recommended free-tier option. It provides access to 10 models at zero cost.

### Endpoint

```
https://opencode.ai/zen/go/v1
```

### Authentication

Uses Bearer token authentication. Any non-empty API key is accepted for validation, but a valid key from opencode.ai is required for actual generation.

### Validation

```
Method:  POST /chat/completions
Timeout: 30 seconds
Body:    { "model": "deepseek-v4-flash", "messages": [{"role":"user","content":"Say OK"}] }
```

Validation sends a minimal test message to confirm the key works. If the provider responds successfully, all 10 Go models are marked as available.

### Generation

```
Method:  POST /chat/completions
Timeout: None (waits indefinitely)
Stream:  false
```

> [!WARNING]
> Generation requests to OpenCode Go have no timeout. If the provider is slow or unresponsive, the request will block indefinitely. Consider monitoring long-running generations and cancelling if needed.

## API Reference

### List Credentials

```
GET /api/v1/provider-credentials
```

Returns paginated list of credentials (secrets stripped).

### Get Credential

```
GET /api/v1/provider-credentials/:id
```

Returns a single credential (secrets stripped).

### Create Credential

```
POST /api/v1/provider-credentials
Content-Type: application/json

{
  "provider": "openai",
  "apiKey": "sk-...",
  "defaultModel": "gpt-4o-mini",
  "displayName": "My OpenAI Key"
}
```

### Update Credential

```
PUT /api/v1/provider-credentials/:id
Content-Type: application/json

{
  "apiKey": "sk-new-...",
  "defaultModel": "gpt-4o"
}
```

> [!NOTE]
> Updating the API key resets the credential status to `unverified`. You must re-validate after changing the key.

### Delete Credential

```
DELETE /api/v1/provider-credentials/:id
```

Returns `204 No Content`.

### Validate Credential

```
POST /api/v1/provider-credentials/:id/validate
```

Tests the stored API key against the provider. Returns the updated credential with `valid` or `invalid` status.
