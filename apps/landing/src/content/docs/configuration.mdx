# Configuration

Orchestra is configured through environment variables. All configuration is validated at startup using Zod schemas, and the process will exit with code `1` if any required values are missing or invalid.

## Environment Variables

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `NODE_ENV` | `"development" \| "production" \| "test"` | `"development"` | Runtime environment mode |
| `PORT` | `number` (positive integer) | `3000` | Backend API server port |
| `HOST` | `string` | `"0.0.0.0"` | Backend API server bind address |
| `LOG_LEVEL` | `"fatal" \| "error" \| "warn" \| "info" \| "debug" \| "trace" \| "silent"` | `"info"` | Pino logger verbosity level |
| `DATABASE_URL` | `string` (optional) | — | PostgreSQL connection string. If omitted, SQLite is used |
| `SQLITE_DB_PATH` | `string` | `"./orchestra.db"` | Path to the SQLite database file |
| `ENCRYPTION_KEY` | `string` | — | AES-256-GCM key for encrypting provider API keys at rest |
| `WEB_PORT` | `number` | `3001` | Frontend development server port |
| `NEXT_PUBLIC_API_URL` | `string` | — | Base URL the frontend uses to reach the API |

> [!NOTE]
> All variables are validated at startup. Invalid or missing required values cause the process to exit with code `1`.

## Startup Validation

Orchestra uses Zod schemas to validate every environment variable before the server starts. This ensures misconfigurations fail fast rather than causing cryptic runtime errors.

```ts
// Simplified validation schema
const envSchema = z.object({
  NODE_ENV: z.enum(["development", "production", "test"]).default("development"),
  PORT: z.coerce.number().int().positive().default(3000),
  HOST: z.string().default("0.0.0.0"),
  LOG_LEVEL: z.enum(["fatal", "error", "warn", "info", "debug", "trace", "silent"]).default("info"),
  DATABASE_URL: z.string().url().optional(),
  SQLITE_DB_PATH: z.string().default("./orchestra.db"),
  ENCRYPTION_KEY: z.string().min(1),
  WEB_PORT: z.coerce.number().int().positive().default(3001),
  NEXT_PUBLIC_API_URL: z.string().url(),
});
```

> [!WARNING]
> If validation fails, detailed error messages are logged to stderr showing exactly which variables are invalid and why.

## Database Configuration

Orchestra supports two database backends:

### SQLite (Default)

When `DATABASE_URL` is not set, Orchestra uses SQLite via [sql.js](https://sql.js.org/), a pure JavaScript SQLite implementation compiled to WebAssembly.

- **No native compilation required** — works on any platform Node.js supports
- **Auto-creates** the database file on first startup if it doesn't exist
- **File location** controlled by `SQLITE_DB_PATH` (default: `./orchestra.db`)

> [!TIP]
> SQLite is ideal for local development and single-user deployments. No external database server is needed.

### PostgreSQL

Set `DATABASE_URL` to a valid PostgreSQL connection string to use PostgreSQL instead:

```bash
DATABASE_URL="postgresql://user:password@localhost:5432/orchestra"
```

## Provider Credential Configuration

Provider credentials (API keys for LLM providers) are configured at runtime through the REST API or the web UI. They are never stored in environment variables or config files.

See the [Provider Credentials API](/docs/api-reference#provider-credentials) for programmatic management.

> [!DANGER]
> Never commit API keys to version control. Always use the API or UI to configure provider credentials.

## Encryption

All provider API keys are encrypted at rest using **AES-256-GCM** symmetric encryption.

### Key Derivation

The `ENCRYPTION_KEY` environment variable is processed through **SHA-256** to derive a fixed 256-bit key, regardless of the input length.

### Storage Format

Encrypted values are stored as a colon-delimited string:

```
<iv>:<ciphertext>:<tag>
```

| Component | Description |
|-----------|-------------|
| `iv` | Hex-encoded initialization vector (12 bytes for GCM) |
| `ciphertext` | Hex-encoded encrypted data |
| `tag` | Hex-encoded GCM authentication tag (16 bytes) |

> [!NOTE]
> Each encryption operation uses a unique random IV, so the same plaintext will produce different ciphertext each time.

## Logging

Orchestra uses [Pino](https://getpino.io/) for structured JSON logging. The `LOG_LEVEL` environment variable controls which messages are emitted.

| Level | Description |
|-------|-------------|
| `fatal` | Critical errors that cause process termination |
| `error` | Runtime errors and unexpected conditions |
| `warn` | Potentially harmful situations |
| `info` | General operational information (default) |
| `debug` | Detailed diagnostic information |
| `trace` | Fine-grained event tracing |
| `silent` | All logging disabled |

```json
{"level":30,"time":1700000000000,"pid":1234,"hostname":"localhost","msg":"Server started","port":3000}
```

> [!TIP]
> Set `LOG_LEVEL=debug` during development for detailed request/response logging and internal state information.

## Example `.env` File

```bash
# Runtime
NODE_ENV=development
PORT=3000
HOST=0.0.0.0
LOG_LEVEL=info

# Database (omit DATABASE_URL to use SQLite)
# DATABASE_URL=postgresql://user:password@localhost:5432/orchestra
SQLITE_DB_PATH=./orchestra.db

# Encryption (required — used to encrypt provider API keys at rest)
ENCRYPTION_KEY=your-secret-encryption-key-here

# Frontend
WEB_PORT=3001
NEXT_PUBLIC_API_URL=http://localhost:3000
```

> [!WARNING]
> The `.env` file should never be committed to version control. Add it to your `.gitignore` file.
